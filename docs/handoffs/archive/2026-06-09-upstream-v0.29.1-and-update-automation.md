## Goal

Integrate upstream Memos `v0.29.1` into the `diary-mode` branch and establish a
repeatable, mostly automated process for detecting and preparing future stable
upstream updates.

## Background

- The fork currently uses upstream Memos `v0.29.0` as its base.
- Upstream `v0.29.1` tag commit is
  `5f194da7d3f71a428b437898cdfd073c66a3df38`.
- The tag has already been fetched locally as `upstream-v0.29.1` and `v0.29.1`.
- Official release notes:
  https://github.com/usememos/memos/releases/tag/v0.29.1
- Full comparison:
  https://github.com/usememos/memos/compare/v0.29.0...v0.29.1
- The upstream release includes task-list layout fixes, link-preview metadata
  fixes, mobile video posters, image-preview zoom, `react-use` removal, and CORS
  centralization.
- There are no database migrations or API schema changes.
- Fork/upstream code overlap is limited to:
  - `server/router/api/v1/v1.go`
  - `web/src/hooks/index.ts`
- Those code changes are expected to merge without textual conflict.
- `AGENTS.md` is deleted from Git on the fork but modified by upstream, so the
  merge will report a modify/delete conflict. Resolve it in favor of the fork:
  keep `AGENTS.md` excluded from Git while preserving the local-only file.
- `CLAUDE.md` must also remain local-only and excluded from Git.

## Automation Design

Use this boundary:

- Automatically detect a newer stable upstream tag on a weekly schedule.
- Provide a local PowerShell command that fetches a selected tag, reports files
  changed by both upstream and the fork, protects local-only agent files, and
  performs a `--no-commit` merge.
- Reuse existing CI to test changes and build the image after an explicitly
  reviewed push.
- Do not automatically commit, push, publish an image, or deploy an upstream
  update. A clean Git merge can still cause semantic Diary Mode regressions.

## Implementation Requirements

1. Merge `upstream-v0.29.1` into `diary-mode` with a merge commit structure, but
   do not commit automatically.
2. Resolve the `AGENTS.md` conflict in favor of the fork deletion while
   preserving the local-only file contents.
3. Confirm the fork-specific changes in `server/router/api/v1/v1.go` and
   `web/src/hooks/index.ts` remain present alongside upstream changes.
4. Record `v0.29.1` in `.upstream-version`.
5. Add a weekly and manually dispatchable GitHub Actions check that:
   - reads `.upstream-version`;
   - finds the latest stable `vX.Y.Z` tag from `usememos/memos`;
   - excludes prereleases;
   - writes a useful step summary and makes a newer release visible.
6. Add a PowerShell preparation script suitable for the Windows development
   machine. It must:
   - require a clean `diary-mode` working tree;
   - accept a stable version tag;
   - fetch the selected upstream tag;
   - report fork/upstream overlapping files;
   - preserve local-only `AGENTS.md` and `CLAUDE.md`;
   - use a no-commit merge;
   - update `.upstream-version` only after non-metadata conflicts are resolved;
   - never commit, push, or deploy.
7. Document the detection, review, verification, commit, push, and rollback
   process.

## Constraints

- Preserve existing Memos structure; stay on `diary-mode`.
- Preserve all Diary Mode behavior and feature flags.
- Do not build Go locally; use Docker or note CI verification.
- Keep changes scoped to upstream `v0.29.1` plus the automation/documentation
  files listed above.
- Do not add application dependencies or unrelated build tooling.
- Do not touch secrets, credentials, `.env`, or local settings.
- Do not reintroduce upstream release, demo deployment, stale, or canary
  workflows removed by the fork.
- Keep local-only `AGENTS.md` and `CLAUDE.md` excluded from version control.
- Keep LF line endings.
- Do not commit automatically.

## Non Goals

- Automatically pushing, publishing GHCR images, or deploying upstream updates.
- Updating beyond stable `v0.29.1`.
- Refactoring Diary Mode code.
- Changing Portainer or Raspberry Pi deployment configuration.

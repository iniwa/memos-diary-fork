# Memos Diary Mode 設計書

> **文書の位置づけ（2026-08-05）**: 本書は Memos v0.29.0 を起点にした
> Diary Mode の原設計と段階導入方針を記録する歴史的な設計基準である。現在の
> 統合済み upstream は `.upstream-version`、実装・運用の現況は
> `README.diary.md` と `docs/diary-mode-operations.md`、v0.30.0 追随時の変更は
> `docs/decisions/0003-upstream-v0.30.0-integration.md` を正とする。本書内の
> v0.29.x、初期フェーズ、推奨ブランチ例は現行状態を示す運用指示ではない。

## 1. 概要

本設計書は、OSSメモアプリ **Memos v0.29.0** をベースに、個人用の日記ツールとして拡張するための設計をまとめる。

既存のMemos環境はすでに運用中であるため、現行Memosを直接置き換えず、現行Memosのデータをコピーした **改造版Memos** を別アプリケーションとして構築する。

改造版Memosは、別DB・別Resourceディレクトリ・別ポート・別URLで運用する。

---

## 2. 前提

### 2.1 ベースアプリケーション

- ベース: `usememos/memos`
- バージョン: `v0.29.0`
- 運用形態: Docker
- ホスト環境: Raspberry Pi
- 用途: 個人用の日記 / ライフログ
- 既存Memos環境: 運用中

### 2.2 基本方針

- 現行Memosは直接改造・置換しない
- 現行Memosのデータをコピーして改造版Memosを別アプリとして起動する
- 改造版Memosは別DB / 別Resource / 別ポート / 別URLで運用する
- 動作が良ければ、以後の投稿先を改造版Memosへ統一する
- 現行Memosは参照用・保険として残す
- 初期段階ではDB変更を極力避ける
- UI改修から先に進める
- 画像圧縮などリスクの高い処理は後半で実装する

### 2.3 既存Memosで利用する機能

Memos v0.29.0 には、日記用途に必要な以下の機能が既に存在している。

- カレンダーから日付単位で投稿を確認できる
- `displayTime` を利用して、日記上の日時を扱える
- `createTime` / `updateTime` / `displayTime` により、投稿日時・更新日時・日記日時を区別できる

そのため、本プロジェクトではこれらを新規実装対象とはしない。

本プロジェクトでは、既存機能を前提として、主に以下の不足部分を追加・改修する。

1. タグを本文内ではなく専用セクションで管理する
2. 画像添付をファイル添付風ではなく、投稿内に埋め込み表示する
3. 画像アップロード時に自動圧縮・サムネイル生成を行う
4. 必要に応じて、日記用途に合うよう既存UIの表示名・導線を調整する

---

## 3. 目的

Memos v0.29.0 の既存機能を活かしつつ、個人用の日記ツールとしてより使いやすくする。

本プロジェクトの主な目的は以下である。

- タグを本文内ではなく、専用セクションで管理できるようにする
- 画像添付をファイル添付風ではなく、投稿内に埋め込み表示できるようにする
- 画像アップロード時に自動圧縮・サムネイル生成できるようにする
- スマホからの日記投稿・画像閲覧が快適になるよう、表示UIを調整する
- 既存Memos環境のデータを維持したまま、日記用途に適した操作感へ寄せる

---

## 4. 対象機能

### 4.1 対象にする機能

本プロジェクトで追加・変更する主な機能は以下。

1. タグ専用セクション
2. Twitter/X風画像グリッド表示
3. 画像付き投稿フィルタ
4. 画像アップロード時の圧縮処理
5. スマホ閲覧時の画像表示・投稿UIの調整
6. 既存データを使った安全な別アプリ運用

### 4.2 既存機能として利用するもの

以下は Memos v0.29.0 に既に存在するため、新規実装対象とはしない。

- カレンダー表示
- 日付単位での投稿確認
- `displayTime` による日記日時管理
- `createTime` / `updateTime` / `displayTime` の区別

ただし、表示名や導線が日記用途に合わない場合は、軽微なUI調整のみ行う。

### 4.3 初期段階で対象外にする機能

以下は初期MVPでは対象外とする。

- 完全なタグDB分離
- 既存画像の一括圧縮
- 編集履歴機能
- 独自モバイルアプリ
- 複数ユーザー向け権限設計の大幅改造
- 動画圧縮
- AIによる日記分類・要約

## 5. 日時仕様

Memos既存の時刻フィールドを以下のように扱う。

| 表示名 | Memos側フィールド | 意味 |
|---|---|---|
| 投稿日時 | `createTime` | 実際に投稿を作成した日時 |
| 更新日時 | `updateTime` | 最後に投稿を更新した日時 |
| 日記日時 | `displayTime` | 日記上の日付・時刻 |

これらは既存Memosに実装済みのため、本プロジェクトでは新規実装対象にしない。

## 6. タグ仕様

### 6.1 基本方針

タグは、ユーザー体験上は本文内に `#tag` と直接記述するのではなく、投稿フォーム内の専用セクションで管理する。

ただし初期実装では、Memos v0.29.0 の既存タグ機構との互換性を優先し、DB構造の変更は行わない。

そのため、内部的には既存の本文内タグ仕様を利用しつつ、UI上ではタグを本文から分離して扱う。

### 6.2 目的

タグ専用セクションの目的は以下である。

- 本文中にタグ文字列が混ざることを避ける
- 日記本文を自然な文章として書きやすくする
- タグ追加・削除をUI操作で行えるようにする
- 既存Memosのタグ検索・タグ一覧との互換性を維持する
- 既存投稿に含まれる `#tag` を破壊しない

### 6.3 UI仕様

投稿作成画面・投稿編集画面に、本文入力欄とは別にタグ入力欄を設ける。

表示例:

```txt
本文
----------------
今日はマリオカートを練習した。
ラウンジでかなり惜しい試合があった。

タグ
----------------
[ゲーム] [マリオカート] [ラウンジ] [+ タグ追加]
```

タグはチップ形式で表示する。

各タグチップには削除ボタンを設ける。

```txt
[ゲーム ×] [マリオカート ×] [ラウンジ ×]
```

### 6.4 タグ入力仕様

タグ入力欄では、以下の操作を可能にする。

- タグ名を直接入力
- Enterでタグ確定
- カンマ区切り入力
- 既存タグ候補から選択
- タグチップの削除
- 重複タグの自動除去

### 6.5 既存本文内タグの読み取り

既存投稿の本文末尾に `#tag` のみで構成されたタグ行がある場合、投稿編集画面ではそれをタグ専用セクションに読み取って表示する。

例:

```md
今日はマリオカートを練習した。

#ゲーム #マリオカート
```

編集画面では以下のように表示する。

```txt
本文
----------------
今日はマリオカートを練習した。

タグ
----------------
[ゲーム] [マリオカート]
```

このとき、本文入力欄ではタグ行を非表示にする方針とする。

### 6.6 保存時の挙動

初期実装では、タグ情報はMemos既存仕様に合わせて本文へ反映する。

保存時には、本文末尾にタグを自動付与する。

例:

```md
今日はマリオカートを練習した。
ラウンジでかなり惜しい試合があった。

#ゲーム #マリオカート #ラウンジ
```

これにより、Memos既存のタグ検索・タグ一覧・ショートカット条件との互換性を維持する。

### 6.7 本文表示時の挙動

投稿表示時には、本文末尾のタグ行を本文として表示せず、タグ専用表示へ分離する。

表示例:

```txt
今日はマリオカートを練習した。
ラウンジでかなり惜しい試合があった。

タグ:
[ゲーム] [マリオカート] [ラウンジ]
```

### 6.8 タグ行の判定ルール

初期実装では、本文末尾にあるタグのみの行を「タグ行」として扱う。

タグ行の例:

```md
#ゲーム #マリオカート #ラウンジ
```

以下のように、文章中に自然に含まれる `#` はタグ専用セクションへ移動しない。

```md
今日は #マリオカート の練習をした。
```

### 6.9 階層タグ / グループタグ

Memosでは、`/` 区切りのタグを利用することで、タグを階層的にグループ化できる。

例:

- `#PC/mic`
- `#food/hamburger`
- `#game/FF14`
- `#restaurant/ブロンコビリー`

本プロジェクトのタグ専用セクションでも、この階層タグ仕様を維持する。

タグ入力欄では `/` を含むタグ名を許可する。  
保存時にも `/` を除去・変換せず、Memos既存仕様に合わせて本文末尾へ反映する。

### 6.10 `#photo` タグの廃止

画像付き投稿を表すための `#photo` タグは、今後は使用しない。

画像付き投稿かどうかは、投稿本文中のタグではなく、投稿に紐づくResource情報から自動判定する。

新規投稿時に画像を添付しても、`#photo` は自動付与しない。

既存投稿に `#photo` が含まれている場合、初期段階では自動削除しない。

### 6.11 タグ名の正規化

初期実装では、以下の正規化を行う。

- 先頭の `#` は自動除去
- 前後の空白は削除
- 空文字タグは保存しない
- 重複タグは保存しない
- `/` は保持する
- 日本語は保持する
- 大文字小文字は既存Memos仕様に合わせる

### 6.12 既存データへの影響

この方式ではDB構造を変更しないため、既存投稿への影響は最小限となる。

既存投稿は、編集・保存されるまでは原則として本文を変更しない。

既存投稿を編集保存した場合のみ、本文末尾のタグ行が新仕様に合わせて整形される。

### 6.13 将来拡張

将来的に、タグを本文から完全分離したくなった場合は、以下のDB構造を検討する。

```txt
tag
memo_tag
```

ただし、この方式では以下の作業が必要になる。

- DB migration
- 既存本文内タグからの移行処理
- API変更
- フロントエンド変更
- 既存Memosタグ機能との互換性整理

そのため、初期段階では実施しない。

## 7. 画像表示仕様

### 7.1 基本方針

投稿に添付された画像Resourceは、従来の「添付ファイル」表示ではなく、投稿本文の下に埋め込み表示する。

非画像Resourceは、従来通り添付ファイルとして表示する。

これにより、日記投稿内の写真を自然に閲覧できるようにする。

### 7.2 Resource分類

投稿に紐づくResourceは、MIME typeを基準に以下の2種類へ分類する。

```txt
imageResources:
  画像として投稿内に埋め込み表示するResource

fileResources:
  添付ファイルとして表示するResource
```

画像Resourceとして扱うMIME typeは以下。

```txt
image/jpeg
image/png
image/webp
image/gif
image/avif
image/svg+xml
```

上記以外のResourceは、原則として非画像ファイルとして扱う。

### 7.3 表示位置

画像Resourceは、投稿本文の直下に表示する。

表示順は以下とする。

```txt
1. 日記本文
2. 画像グリッド
3. 非画像添付ファイル
4. タグ表示
5. メタ情報 / 操作ボタン
```

### 7.4 画像枚数ごとのレイアウト

画像枚数に応じて、以下のように表示する。

| 画像枚数 | 表示 |
|---:|---|
| 1枚 | 横幅いっぱいに大きく表示 |
| 2枚 | 横2カラム |
| 3枚 | 左1枚大きく、右2枚を縦並び |
| 4枚 | 2×2グリッド |
| 5枚以上 | 4枚表示し、4枚目に `+N` オーバーレイ |

### 7.5 画像クリック / タップ時の挙動

画像をクリックまたはタップした場合、画像プレビューを開く。

初期実装では、Memos既存の画像プレビュー機能を利用する。

画像プレビューでは以下を満たす。

- 選択した画像から表示を開始する
- 複数画像がある場合は前後移動できる
- スマホではスワイプ操作に対応することが望ましい
- Escキーまたは背景クリックで閉じられる
- 拡大表示では `preview` を優先して使う

### 7.6 スマホ表示

スマホでは、投稿カードの横幅に合わせて画像グリッドを表示する。

スマホ表示で重視する点は以下。

- 横スクロールを発生させない
- タップ領域を十分に確保する
- 画像同士の隙間を小さくする
- 角丸を維持する
- 縦長画像で投稿カードが長くなりすぎないようにする

### 7.7 非画像ファイルの表示

画像ではないResourceは、従来通り添付ファイルとして表示する。

例:

```txt
添付ファイル:
- receipt.pdf
- memo.zip
- document.txt
```

画像Resourceと非画像Resourceが混在している場合は、画像をグリッド表示し、非画像ファイルをその下に表示する。

### 7.8 画像付き投稿の判定

投稿に画像Resourceが1件以上存在する場合、その投稿を「画像付き投稿」として扱う。

この判定は `#photo` タグには依存しない。

```txt
imageResources.length > 0
```

### 7.9 読み込み最適化

投稿一覧では、画像は遅延読み込みする。

```txt
loading="lazy"
```

画像グリッドでは、可能であれば `thumbnail` または `preview` を優先して読み込む。

## 8. 画像付き投稿フィルタ仕様

### 8.1 基本方針

画像付き投稿は、本文内タグではなく、投稿に紐づくResource情報から自動判定する。

従来のように `#photo` タグで画像付き投稿を管理する方式は採用しない。

### 8.2 判定条件

投稿に画像Resourceが1件以上存在する場合、その投稿を「画像付き投稿」として扱う。

```txt
画像付き投稿 = imageResources.length > 0
```

### 8.3 フィルタ種別

初期実装では、以下のフィルタのみを実装対象とする。

```txt
画像付き投稿のみ
```

将来的な拡張候補として、以下を検討する。

```txt
添付あり投稿:
  Resourceが1件以上ある投稿

ファイル付き投稿:
  非画像Resourceが1件以上ある投稿
```

### 8.4 UI仕様

投稿一覧・検索画面・ショートカット相当の絞り込みUIに、画像付き投稿フィルタを追加する。

表示例:

```txt
[すべて] [画像付き]
```

初期実装では、既存Memos UIとの親和性を優先し、フィルタチップ形式を基本とする。

### 8.5 タグ検索との組み合わせ

画像付き投稿フィルタは、タグ検索と組み合わせ可能とする。

例:

```txt
タグ: restaurant/ブロンコビリー
フィルタ: 画像付き
```

この場合、以下の条件を満たす投稿のみを表示する。

```txt
1. restaurant/ブロンコビリー タグを持つ
2. image/* Resourceを1件以上持つ
```

### 8.6 カレンダーとの組み合わせ

初期実装では、カレンダー表示自体は既存Memosの機能を利用する。

画像付き投稿フィルタをカレンダーに直接反映するかは、初期実装では必須としない。

### 8.7 API側 / フロント側の判定

初期実装では、既存APIで取得できるResource情報をもとに、フロントエンド側で画像付き投稿を判定する。

理由:

- DB変更を避けられる
- API変更を最小化できる
- 既存データへの影響が少ない
- 実装範囲を小さくできる

将来的にはAPI側フィルタを追加する。

## 9. 画像圧縮仕様

### 9.1 基本方針

画像アップロード時に、元画像を一時保存したうえで、`preview` および `thumbnail` を生成する。

Raspberry Pi上での運用を想定するため、アップロードAPIのレスポンスを画像圧縮完了まで待たせない。

画像圧縮は新規アップロード画像のみを対象とする。  
既存画像は初期段階では再圧縮しない。

### 9.2 対象画像

圧縮対象とするMIME typeは以下。

```txt
image/jpeg
image/png
image/webp
```

初期実装では、以下は圧縮対象外とする。

```txt
image/gif
image/avif
image/svg+xml
```

### 9.3 生成する画像

画像アップロード後、以下の3種類の画像を扱う。

```txt
original:
  アップロードされた元画像

preview:
  クリック後の拡大表示に使用する低圧縮・高品質画像

thumbnail:
  投稿内グリッド、一覧、将来のカレンダー表示に使用する軽量画像
```

派生画像は `preview` と `thumbnail` の2系統に絞る。

`display` 画像は作成しない。

### 9.4 元画像の保持

通常運用では、元画像は原則として保持しない。

画像アップロード時には、一時的に original を保存する。  
その後、`preview` / `thumbnail` の生成に成功した場合、original は削除する。

理由:

- Raspberry Pi上のストレージ使用量を抑えられる
- 日記用途では、閲覧用の高品質 preview があれば十分な場合が多い
- バックアップ対象の容量を小さくできる
- 画像圧縮機能の目的と整合する

圧縮に失敗した場合は、画像消失を防ぐため、original をfallbackとして保持する。

初回検証時・初回本番投入時は、安全側として `MEMOS_IMAGE_KEEP_ORIGINAL=true` を使ってもよい。

安定確認後、通常運用として `MEMOS_IMAGE_KEEP_ORIGINAL=false` へ切り替える。

### 9.5 preview画像の仕様

`preview` は、投稿画像をクリック / タップした後の拡大表示で使用する。

| 項目 | 値 |
|---|---|
| 用途 | 拡大表示 |
| 最大長辺 | 2560px |
| 出力形式 | JPEG |
| JPEG品質 | 90 |
| EXIF | 原則削除 |
| 拡大 | しない |
| 縮小 | 最大長辺を超える場合のみ行う |

### 9.6 thumbnail画像の仕様

`thumbnail` は、投稿内画像グリッド、一覧表示、将来的なカレンダー画像表示で使用する。

| 項目 | 値 |
|---|---|
| 用途 | 投稿内グリッド / 一覧 / カレンダー候補 |
| 最大長辺 | 720px |
| 出力形式 | JPEG |
| JPEG品質 | 78 |
| EXIF | 削除 |
| 拡大 | しない |
| 縮小 | 最大長辺を超える場合のみ行う |

### 9.7 UI側の画像選択優先順位

#### 投稿カード内グリッド

```txt
1. thumbnail
2. preview
3. original
```

#### 1枚画像の投稿内表示

```txt
1. preview
2. thumbnail
3. original
```

#### 画像クリック後の拡大表示

```txt
1. preview
2. original
3. thumbnail
```

### 9.8 処理フロー

画像アップロード時の処理フローは以下。

```txt
1. ユーザーが画像をアップロード
2. Memosがoriginal Resourceを一時保存
3. Resource作成レスポンスを返す
4. バックグラウンドで画像圧縮ジョブを開始
5. preview画像を生成
6. thumbnail画像を生成
7. Resource metadataに生成結果を保存
8. 圧縮成功後、originalを削除する
9. UI側は生成済み画像があれば優先して利用する
```

重要点:

```txt
アップロード操作自体は、圧縮完了を待たない。
```

### 9.9 Resource metadata

圧縮画像の状態は、Resource metadataに保存する。

保存する情報の例:

```json
{
  "imageProcessing": {
    "status": "done",
    "originalKept": false,
    "previewPath": "...",
    "thumbnailPath": "...",
    "originalWidth": 4032,
    "originalHeight": 3024,
    "previewWidth": 2560,
    "previewHeight": 1920,
    "thumbnailWidth": 720,
    "thumbnailHeight": 540,
    "processedAt": "2026-05-29T12:00:00Z"
  }
}
```

statusは以下を想定する。

```txt
pending:
  処理待ち

processing:
  処理中

done:
  処理完了

failed:
  処理失敗

skipped:
  圧縮対象外
```

### 9.10 Piでの負荷対策

Raspberry Pi上での運用を想定し、画像圧縮処理は同時実行数を制限する。

初期設定:

```txt
画像圧縮ジョブ同時実行数: 1
```

### 9.11 設定項目

初期実装では、以下の環境変数を検討する。


### 9.12 初期実装の範囲

初期実装では以下を対象とする。

- 新規アップロード画像のみ処理
- JPEG / PNG / WebP の基本的な画像判定
- preview画像生成
- thumbnail画像生成
- originalは通常運用では保持しない
- 非同期処理
- 同時実行数1
- 失敗時originalフォールバック

## 10. 移行・検証・運用切り替え仕様

### 10.1 基本方針

本プロジェクトでは、既存の Memos v0.29.0 環境を直接置き換えない。

現行Memosのデータをコピーし、改造版Memosは別データベース・別データディレクトリ・別ポートで起動する。

改造版Memosは、既存Memosのアップデートではなく、独立した別アプリケーションとして扱う。

### 10.2 運用構成

```txt
現行Memos:
  既存の本番環境
  既存DBを利用
  既存Resourceディレクトリを利用
  継続して利用可能

改造版Memos:
  現行Memosのデータコピーから開始
  別DBを利用
  別Resourceディレクトリを利用
  別ポート / 別URLで起動
```

構成例:

```txt
現行Memos:
  container: memos
  port: 5230
  data: ./memos-data
  url: https://memos.example.com

改造版Memos:
  container: memos-diary
  port: 5231
  data: ./memos-diary-data
  url: https://diary.example.com
```

### 10.3 データコピー方針

改造版Memosの初期データは、現行Memosのデータをコピーして作成する。

SQLite運用の場合:

```bash
cp -a ./memos-data ./memos-diary-data
```

PostgreSQL運用の場合:

```bash
docker exec memos-db pg_dump -U memos memos > memos-backup.sql
```

その後、改造版Memos用DBへrestoreする。

Resource / 添付ファイル保存ディレクトリも、改造版用にコピーする。

### 10.4 データ分岐に関する注意

データコピー後、現行Memosと改造版Memosは別データとして分岐する。

そのため、コピー後に現行Memosへ投稿した内容は、改造版Memosには自動反映されない。

同様に、改造版Memosへ投稿した内容も、現行Memosには反映されない。

したがって、検証後に改造版Memosを使い続ける場合は、どこかのタイミングで以下を決める必要がある。

```txt
以後の正環境:
  改造版Memos

現行Memos:
  参照用 / 保険 / アーカイブ
```

### 10.5 切り替え方針

改造版Memosの動作が良好であれば、以後は改造版Memosを日記ツールとして使い続ける。

この場合、現行Memosは即削除せず、一定期間は読み取り用・保険として保持する。

推奨:

```txt
1. 現行Memosから改造版Memosへデータコピー
2. 改造版Memosを別URLで起動
3. 数日〜数週間、改造版Memosを試用
4. 問題がなければ、以後の投稿先を改造版Memosへ統一
5. 現行Memosは参照用として残す
6. 十分に安定したら、必要に応じて現行Memosを停止
```

### 10.6 推奨判断

本プロジェクトでは、既存Memos環境の安全性を優先し、以下の方針を採用する。

```txt
現行Memosを直接改造・置換しない。
現行Memosのデータコピーから、改造版Memosを別アプリとして起動する。
動作が良好であれば、以後は改造版Memosを使い続ける。
```

## 11. 実装フェーズ / タスク分解

### 11.1 基本方針

改造版Memosは、現行Memosとは別アプリとして構築する。

そのため、本番の現行Memos環境には直接変更を加えない。

実装は以下の方針で進める。

- Memos v0.29.0 をベースにする
- 改造版Memos用の独立ブランチを作成する
- 現行Memosのデータをコピーして検証する
- 初期段階ではDB変更を避ける
- UI改修から先に進める
- 画像圧縮などリスクの高い処理は後半で実装する

### 11.2 ブランチ構成

推奨ブランチ構成は以下。

```txt
main
  本家Memos v0.29.0相当

diary-mode
  日記ツール化の統合ブランチ

feature/tag-section
  タグ専用セクション実装

feature/image-grid
  Twitter風画像グリッド実装

feature/image-filter
  画像付き投稿フィルタ実装

feature/image-optimizer
  画像圧縮処理実装

feature/deployment
  Docker / Compose / 環境変数整理
```

### 11.3 Phase 0: ベース環境準備

目的:

Memos v0.29.0 をベースに、改造版Memosの開発・検証環境を用意する。

作業内容:

```txt
- usememos/memos を fork
- v0.29.0 タグを基準に diary-mode ブランチを作成
- ローカル開発環境で起動確認
- Docker imageをビルドできることを確認
- 改造版用のdocker-compose.ymlを作成
- 現行Memosとは別ポートで起動できることを確認
```

### 11.4 Phase 1: タグ専用セクション

目的:

本文内に直接 `#tag` を書く運用から、UI上はタグ専用セクションで管理する運用へ変更する。

作業内容:

```txt
- 投稿作成フォームにタグ入力欄を追加
- 投稿編集フォームにタグ入力欄を追加
- 本文末尾のタグ行を解析してタグ欄へ表示
- タグ欄の内容を保存時に本文末尾へ反映
- タグチップUIを作成
- 既存タグ候補のサジェストを追加
- / 区切りの階層タグを保持
- #photo を通常運用から外す
```

### 11.5 Phase 2: 画像グリッド表示

目的:

画像Resourceを従来の添付ファイル表示ではなく、投稿本文下にTwitter/X風グリッドとして表示する。

### 11.6 Phase 3: 画像付き投稿フィルタ

目的:

`#photo` タグに依存せず、画像Resourceの有無から画像付き投稿を絞り込めるようにする。

### 11.7 Phase 4: 画像圧縮処理

目的:

新規アップロード画像に対して、`preview` と `thumbnail` を生成し、通常運用では元画像を保持しない。

### 11.8 Phase 5: Docker / 運用設定

目的:

改造版Memosを、現行Memosとは独立した別アプリとして安定運用できるようにする。

### 11.9 Phase 6: 試用・切り替え判断

目的:

改造版Memosを別アプリとして試用し、問題がなければ日記用の正環境として使い続ける。

### 11.10 優先順位

| 優先度 | Phase | 内容 |
|---:|---|---|
| 1 | Phase 0 | ベース環境準備 |
| 2 | Phase 1 | タグ専用セクション |
| 3 | Phase 2 | 画像グリッド表示 |
| 4 | Phase 3 | 画像付き投稿フィルタ |
| 5 | Phase 5 | Docker / 運用設定 |
| 6 | Phase 4 | 画像圧縮処理 |
| 7 | Phase 6 | 試用・切り替え判断 |

画像圧縮はリスクが高いため、画像表示・タグUI・別アプリ運用が安定してから実装する。

### 11.11 初期MVP

初期MVPでは以下を達成する。

```txt
- 改造版Memosを別アプリとして起動できる
- 既存データコピーで投稿が表示できる
- タグ専用セクションでタグを扱える
- 画像が投稿内にグリッド表示される
- 画像付き投稿フィルタが使える
```

初期MVPでは、画像圧縮は必須としない。

画像圧縮はMVP後、安定確認が取れてから追加する。

## 12. 本家Memos追従方針

### 12.1 基本方針

改造版Memosは、Memos v0.29.0 をベースにしたforkとして開発する。

ただし、本家Memosに `v0.29.1`、`v0.29.2` などの不具合修正・セキュリティ修正・軽微な改善が入った場合、それらを可能な限り改造版Memosにも取り込む。

そのため、本プロジェクトでは以下を基本方針とする。

```txt
本家Memosへの追従を前提に、改造範囲を局所化する。
```

### 12.2 追従対象

優先して取り込む本家更新は以下。

```txt
- セキュリティ修正
- データ破損に関わる不具合修正
- Resource / 添付ファイル周りの修正
- 認証・権限周りの修正
- Docker / migration / 起動処理の修正
- v0.29.x 系の不具合修正
```

一方で、以下は即時追従を必須としない。

```txt
- 大規模なUI変更
- v0.30.0 以降の破壊的変更
- 日記用途と関係が薄い新機能
- 改造版Memosの仕様と衝突する機能
```

### 12.3 ブランチ運用

推奨ブランチ構成は以下。

```txt
upstream-v0.29
  本家Memos v0.29.x を追従するブランチ

diary-mode
  改造版Memosの統合ブランチ

feature/*
  個別機能の開発ブランチ
```

本家更新が出た場合は、まず `upstream-v0.29` に取り込む。

その後、`diary-mode` へ merge または rebase する。

```txt
本家Memos
  ↓
upstream-v0.29
  ↓
diary-mode
  ↓
改造版Memos image
```

### 12.4 改造範囲の局所化

本家追従を容易にするため、改造箇所は可能な限り局所化する。

特に以下を意識する。

```txt
- 既存コンポーネントを直接大きく書き換えない
- 追加コンポーネントとして実装する
- 既存APIの仕様変更を最小化する
- DB migrationを初期段階では避ける
- 既存Resource構造をなるべく壊さない
- 日記専用処理は diary / image / tag などの独立したモジュールへ寄せる
```

### 12.5 衝突しやすい領域

本家更新時に衝突しやすい領域は以下。

```txt
- Memo作成 / 編集フォーム
- Resource表示コンポーネント
- タグ表示・タグ解析処理
- 画像プレビュー処理
- Resourceアップロード処理
- migration
- API型定義
```

これらの領域を改造する場合は、変更理由と仕様を設計書・コメント・コミットメッセージに明記する。

### 12.6 バージョン表記

改造版Memosでは、本家バージョンと改造版バージョンを分けて管理する。

例:

```txt
本家ベース:
  memos v0.29.0

改造版:
  diary-mode v0.1.0
```

本家 `v0.29.1` を取り込んだ場合は、以下のように記録する。

```txt
本家ベース:
  memos v0.29.1

改造版:
  diary-mode v0.1.1
```

表示例:

```txt
Memos Diary Mode v0.1.1
Based on Memos v0.29.1
```

### 12.7 追従ログ

本家更新を取り込んだ場合、追従ログを残す。

記録する内容:

```txt
- 取り込んだ本家バージョン
- 取り込んだ日付
- merge / rebase / cherry-pick のどれを使ったか
- conflictが発生した箇所
- 手動調整した内容
- 動作確認結果
```

### 12.8 設計上の結論

改造版Memosは、完全な独自アプリとして本家から切り離すのではなく、Memos本家の修正を取り込めるforkとして運用する。

そのため、実装時には以下を重視する。

```txt
- 改造範囲を小さく保つ
- 既存機能を置き換えるのではなく拡張する
- DB変更を避けられる場合は避ける
- Resource / Tag / Memo周りの変更は局所化する
- 本家追従時のconflictを想定しておく
```
